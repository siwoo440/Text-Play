# 로컬 설정·데이터 관리 설계

---

## 1. 목표

외부 서버 없이 프로필, 화면, 알림, 대화와 사용자 데이터를 실제로 저장·복구할 수 있는 로컬 설정 흐름을 완성한다. 기존 `AppState`, Reducer, `AppProvider`, `LocalStorageGateway` 구조를 유지하고 스키마를 4에서 5로 올린다.

---

## 2. 범위

- `/settings` 설정 화면
- 프로필 닉네임·아바타 변경
- 플랫폼·해상도·레이아웃 설정
- 선제 메시지·알림 시간·일일 제한 설정
- 전체 상태 JSON 내보내기
- JSON 가져오기 전 검증·미리보기·마이그레이션
- 초기화 직전 자동 백업과 최근 백업 복구
- 대화 제목 변경·보관·복구·삭제·단일 내보내기
- LocalStorage 스키마 4에서 5로 자동 마이그레이션
- 모바일·태블릿·데스크톱 반응형 설정 화면

실제 회원 인증, 서버 동기화, 클라우드 백업, 이메일·푸시 전송, 결제와 원격 데이터베이스는 포함하지 않는다.

---

## 3. 선택한 구조

A안인 단일 상태 확장을 사용한다. 모든 사용자 데이터는 하나의 `AppState`에 유지하고 모든 변경은 Reducer 액션을 통과한다. `AppProvider`는 상태 변경을 감지해 `LocalStorageGateway`에 저장한다.

설정과 콘텐츠를 별도 저장 키로 나누지 않는다. IndexedDB도 이번 단계에서 도입하지 않는다. 데이터 규모가 현재 LocalStorage 운영 범위를 벗어났다는 증거가 없고, 분리 저장이나 데이터베이스 전환은 백업·마이그레이션 복잡성을 불필요하게 증가시키기 때문이다.

---

## 4. 데이터 구조

`AppState.schemaVersion`을 5로 변경한다.

`Conversation`에는 `archivedAt: string | null`을 추가한다. 스키마 4의 모든 기존 대화는 `archivedAt: null`로 변환한다.

프로필은 기존 `UserProfile`을 유지한다. 설정 화면에서는 `nickname`과 `avatar`만 변경할 수 있고, `id`, `membership`, `createdAt`은 변경하지 않는다.

기존 `AppSettings` 필드를 그대로 사용한다.

- `platformMode`
- `layoutId`
- `resolutionMode`
- `proactiveMessageEnabled`
- `notificationStartTime`
- `notificationEndTime`
- `dailyNotificationLimit`
- 패널 열림 상태

백업 이력은 최근 3개만 유지한다. 초기화와 가져오기 직전에 현재 상태를 백업한다.

---

## 5. 화면 구성

`/settings`는 프로필, 화면, 알림, 데이터 관리, 개인정보 안내의 다섯 영역으로 구성한다.

데스크톱은 왼쪽 섹션 탐색과 오른쪽 내용의 2열 구조를 사용한다. 모바일은 가로 스크롤 가능한 상단 탭과 단일 열 내용을 사용한다. 모든 조작 요소는 최소 44px 터치 영역을 확보한다.

선택형 설정은 즉시 저장한다. 닉네임·아바타와 시간 입력은 사용자가 저장 버튼을 눌렀을 때 검증한 뒤 반영한다. 화면에는 저장 중, 저장 완료, 저장 실패 상태를 라이브 영역으로 표시한다.

---

## 6. 데이터 내보내기

전체 내보내기는 현재 `AppState`를 들여쓴 JSON 파일로 다운로드한다. 파일에는 제작자 비공개 프롬프트와 대화 내용이 포함될 수 있으므로 다운로드 전에 개인정보 경고를 표시한다.

손상 데이터 백업이 존재하면 별도의 백업 JSON으로 내려받을 수 있게 한다. 단일 대화 내보내기는 대화 메타데이터와 해당 메시지만 포함한다.

---

## 7. 데이터 가져오기

가져오기는 다음 순서를 지킨다.

1. 파일 형식과 크기 확인
2. JSON 분석
3. 상태 구조와 스키마 버전 확인
4. 지원되는 이전 버전 마이그레이션
5. 캐릭터·대화·메시지·보관 수 미리보기
6. 사용자 확인
7. 현재 상태 자동 백업
8. 새 상태 교체·저장

분석, 검증 또는 저장이 실패하면 기존 상태를 변경하지 않는다. 현재 버전보다 높은 미래 스키마는 가져오지 않고 지원하지 않는 버전임을 표시한다.

---

## 8. 초기화와 복구

초기화 확인창에는 삭제될 캐릭터, 대화와 메시지 수를 표시한다. 승인 시 현재 상태를 자동 백업한 뒤 초기 상태로 교체한다. 초기화는 자동 백업을 제거하지 않는다.

복구 화면은 최근 백업의 생성 시각과 데이터 수를 표시한다. 복구 전에 현재 상태도 다시 백업해 연속 실수를 되돌릴 수 있게 한다.

---

## 9. 대화 관리

보관함의 진행 중인 대화 탭에 다음 동작을 추가한다.

- 제목 변경
- 보관
- 보관 해제
- 삭제
- JSON 내보내기

대화 삭제는 연결된 메시지를 같은 Reducer 처리 안에서 제거한다. 현재 선택된 대화가 삭제되면 `selectedConversationId`를 `null`로 변경한다.

---

## 10. 오류 처리

- LocalStorage 용량 부족: 현재 입력 유지와 저장 실패 안내
- 손상 JSON: 가져오기 중단과 기존 상태 유지
- 지원하지 않는 스키마: 지원 버전 안내
- 마이그레이션 실패: 원본 백업과 초기 상태 복구
- 백업 저장 실패: 초기화·가져오기 중단
- 존재하지 않는 대화: 상태 변경 없이 오류 안내

데이터를 잃을 수 있는 동작은 저장 성공을 확인한 뒤 다음 단계로 진행한다.

---

## 11. 테스트

단위 테스트는 프로필·설정 Reducer, 대화 이름 변경·보관·삭제, 스키마 4에서 5 마이그레이션, 가져오기 검증, 백업 순환과 초기화를 검증한다.

통합 테스트는 설정 저장 후 새로고침 복원, 내보내기·가져오기 왕복, 잘못된 파일의 비파괴 처리, 초기화 취소·승인·복구, 대화 삭제 시 메시지 정리를 검증한다.

화면 테스트는 데스크톱 2열, 모바일 단일 열, 키보드 조작, 라이브 상태 안내와 애니메이션 감소 설정을 확인한다.

---

## 12. 사업계획서 반영

구현과 검증이 완료되면 사업계획서의 `11. 챗봇 서비스 사업` 탭 아래에 `11.10 로컬 저장 구조 평가·확장 계획` 하위 탭을 추가한다.

하위 탭에는 다음 내용을 기록한다.

- A안 단일 상태 확장 채택과 실제 구현 범위
- B안 설정 저장소 분리의 장단점과 재평가 조건
- C안 IndexedDB 전환의 장단점과 전환 조건
- LocalStorage 용량 한계나 대용량 파일 저장이 확인될 때의 단계적 이전 원칙
- Text-Play 패키지·이미지 Blob·대규모 대화 저장 시 C안 우선 검토

확인되지 않은 용량 수치나 전환 일정은 확정값처럼 기록하지 않는다.

---

## 13. 완료 기준

- `/settings`의 모든 메뉴가 실제 화면으로 연결
- 프로필·화면·알림 설정이 새로고침 후 유지
- 전체 상태와 단일 대화 내보내기 가능
- 검증된 JSON만 가져오기 가능
- 초기화·가져오기 전에 자동 백업 생성
- 최근 백업 복구 가능
- 대화 제목 변경·보관·삭제 가능
- 기존 스키마 4 데이터 손실 없이 스키마 5로 변환
- 단위·통합 테스트, 타입 검사, ESLint와 프로덕션 빌드 통과
- 사업계획서 11번 탭 아래 `11.10` 하위 탭 생성과 내용 검증

---

## 14. 구현 결과

A안 구현을 완료했다. 앱 상태는 스키마 5로 전환했고, 프로필·화면·알림 설정과 대화 관리 동작은 Reducer를 통해 변경된 뒤 LocalStorage에 저장된다.

데이터 관리 화면에는 개인정보 확인 후 전체 JSON 내보내기, 검증 미리보기 기반 가져오기, 최근 3개 로컬 백업, 복구 백업 내보내기, 복구와 초기화 전 자동 백업을 연결했다. 백업 저장에 실패하면 가져오기·복구·초기화를 중단한다.

보관함에는 진행 대화와 보관 대화를 구분해 제목 변경, 보관, 복구, 삭제와 단일 대화 내보내기를 제공한다. 대화 삭제 시 연결 메시지와 현재 선택 상태를 함께 정리한다.

사업계획서에는 `11. 챗봇 서비스 사업`의 자식 탭으로 `11.10 로컬 저장 구조 평가·확장 계획`을 추가했다. 하위 탭 식별자는 `t.gkfzxkkfnjju`이며 부모 탭 식별자는 `t.kcuviofnsbjb`로 확인했다.
